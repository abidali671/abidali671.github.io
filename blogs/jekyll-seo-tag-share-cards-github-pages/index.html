Share Cards on a Jekyll Site on GitHub Pages: One Front Matter Field With jekyll-seo-tag and a Check Before You Push

By Abid Ali, freelance full-stack developer · November 21, 2026

  • GitHub Pages
  • Jekyll
  • jekyll-seo-tag
  • Link Previews

If your GitHub Pages site is built with Jekyll, you already have most of what you need to make every post look good when its link is shared. A single plugin called jekyll-seo-tag writes the title, description, canonical address and share image tags for each page. What it cannot do is decide which picture goes with which post, or notice when you forgot to give it the information it needs.

I set up a small test site with that plugin, built it locally with Jekyll 4.4.1 and jekyll-seo-tag 2.9.1, and read the head of each generated page. This post is what I learned: what the plugin writes on its own, the one front matter field that adds the picture, three small mistakes that produce a broken card, and a check to run before you push.

Switching the plugin on

The plugin is one of those GitHub Pages supports out of the box. You enable it in two places. First in _config.yml:

url: "https://yourname.github.io"
title: Notes by Abid
description: Short notes on small websites.
plugins:
  - jekyll-seo-tag

Then in your layout, inside the head element, add one tag:

{% seo %}

That is all. It replaces the hand-written title and meta tags you may have in the layout, so remove those to avoid writing the same thing twice.

What it writes without any help

For a post with a title and a description in its front matter, the plugin produced these tags in my test build (shortened to the ones that matter):

<meta property="og:title" content="A post with its own card" />
<meta name="description" content="A short description written for the card." />
<link rel="canonical" href="https://example.github.io/notes/2026/11/20/first-post.html" />
<meta property="og:url" content="https://example.github.io/notes/2026/11/20/first-post.html" />
<meta property="og:site_name" content="Notes by Abid" />
<meta property="og:type" content="article" />
<meta name="twitter:card" content="summary_large_image" />

Notice that the canonical address and og:url match, and both are absolute, built from the url and baseurl settings plus the post's path. Posts get og:type set to article and, in my build, also article:published_time and article:modified_time taken from the date in the file name.

If a post has no description, the plugin used the start of the post's text. That is better than nothing, but the first sentence of a post is often an opening line rather than a summary, so writing a description yourself is worth the thirty seconds.

The one field that adds the picture

A page with no image gets no og:image tag at all, and the plugin then sets twitter:card to summary, which is the small-thumbnail style. In my test, the second post without an image came out exactly like that. To get a wide card, add image to the post's front matter:

---
layout: default
title: "A post with its own card"
description: "A short description written for the card."
image: /assets/card-first.png
---

With that single line the build wrote an absolute og:image, matching twitter:image, and switched twitter:card to summary_large_image:

<meta property="og:image" content="https://example.github.io/notes/assets/card-first.png" />
<meta name="twitter:card" content="summary_large_image" />
<meta name="twitter:image" content="https://example.github.io/notes/assets/card-first.png" />

You write a path; the plugin turns it into a full address. The path starts at the root of the site, and the baseurl is added for you.

Size and alt text

The field also accepts an object, which lets you add dimensions and alt text. My third test post used this form:

image:
  path: /assets/card-first.png
  width: 1200
  height: 630
  alt: "Blue rectangle used as a test card"

The result included og:image:width, og:image:height, og:image:alt and twitter:image:alt. Alt text on the card image costs one line and helps anyone using a screen reader, so I recommend it.

A default image for the whole site

If most pages should share one picture, put it in defaults in _config.yml, and override it per post when a post has its own:

defaults:
  - scope:
      path: ""
    values:
      image: /assets/card-first.png

In my test, even the home page and the post with no image of its own then received a large card with that picture. Pages with their own image keep it.

Three mistakes that break the card

1. No url in the configuration

This was the most useful thing I found. I removed the url line from _config.yml and rebuilt locally. The page no longer had a canonical link or an og:url line, and og:image became a path only:

<meta property="og:image" content="/notes/assets/card-first.png" />

A path without a domain is the classic reason a card shows no picture, because the app that reads the page has no idea which site it belongs to. On GitHub Pages the address is often filled in for you from the repository settings, so you may never see this online. I would still set url explicitly, so the result does not depend on where the site is built. The guide to missing og:image pictures lists this and the other usual causes.

2. A forgotten image on the posts that matter

Without an image, a post gets the small summary card. The plugin does not warn you, and the page looks perfectly fine in your browser. Add the field to the posts you expect to be shared, or set a default. The note on missing Twitter Card tags explains the difference between the two card types.

3. A future date in the file name

Jekyll skips posts dated in the future when it builds. While testing I created a post one day ahead, and the build printed "Skipping: ... has a future date" and generated no page. On a site you update from several machines, a mismatch in the clock or the time zone can make a post disappear from the site until its date arrives. If a new post does not show up, check the date first.

Check before you push

The plugin makes the tags, but it cannot tell you whether they say what you meant. After building, open the generated file and look at the head of one new post. You are looking for five things: an absolute og:image, a canonical address that matches og:url, a description that reads like a sentence, twitter:card set to summary_large_image, and no leftover duplicate tags from the layout.

After you push and the site is live, paste the post address into a meta tag checker to see the same information from the outside. If the live result differs from your local build, the usual cause is a different url or baseurl.

A short checklist

  • Enable jekyll-seo-tag and add {% seo %} to the head of your layout.
  • Set url and baseurl in _config.yml.
  • Give every shareable post a description and an image.
  • Use the object form of image when you want size and alt text.
  • Set a default image for pages that have none.
  • Remove hand-written share tags from the layout so nothing appears twice.
  • Read the built HTML before you push, then check the live address once.

The plugin does the repetitive part well. Your part is small and specific: a good description, a wide picture and a correct site address. Do those three and every post you publish will arrive in a chat looking like you meant it to.
