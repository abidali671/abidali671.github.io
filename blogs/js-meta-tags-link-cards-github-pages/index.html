Why Meta Tags Added by JavaScript Don't Show in Link Cards: Fixing a Static Page on GitHub Pages

By Abid Ali, freelance full-stack developer · November 21, 2026

  • GitHub Pages
  • JavaScript
  • Meta Tags
  • Link Previews

You build a small page for GitHub Pages and add a few lines of JavaScript that set the title, description and picture for sharing. You open the page in your browser, inspect the head, and everything is there. Then you paste the link into a chat and the card is empty. The page works. The card does not know about it.

This post explains why that happens, shows it with a small tested script, and gives the fix for a plain static page. It applies to any page where share tags are added in the browser, whether by a hand-written script or by a single-page app that has not been set up to produce HTML in advance.

Two ways of reading the same page

A browser downloads the HTML, runs the JavaScript, and shows you the result. What you see in the developer tools is the page after the scripts have run. A link preview crawler works differently. Most of them download the HTML, read the tags in the head, and stop. They do not run your scripts. The guide to meta tags that do not show up describes this behaviour in more detail, including which crawlers are more patient than others. The safest assumption for a small site is that the crawler sees only the HTML your server sends.

That is why checking in the browser proves nothing about the card. The element inspector shows the finished page. The crawler gets the raw file.

A small example that fails

Here is the smallest version of the mistake. The page has no share tags in its HTML. A script, loaded with defer, creates them after the page loads.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Notes</title>
  <script src="meta.js" defer></script>
</head>
<body><h1>Notes</h1></body>
</html>
// Sets share tags in the browser after the page loads. Browsers see them; most link-preview crawlers never run this.
const tags = {
  "og:title": "Notes on small sites",
  "og:description": "Short, tested write-ups.",
  "og:image": "https://example.github.io/cover.png",
};
for (const [property, content] of Object.entries(tags)) {
  const m = document.createElement("meta");
  m.setAttribute("property", property);
  m.content = content;
  document.head.appendChild(m);
}

In a browser this works. Every tag is created. To see what a crawler sees, I wrote a script that reads the same file twice: once without running scripts, and once the way a browser would, with scripts on. It uses jsdom, a DOM for Node, and compares the og: tags in each version.

// compare-raw-vs-dom.mjs <dir> : read <dir>/index.html as a crawler would (no JavaScript), then as a browser would (JavaScript on).
import { readFileSync } from "node:fs";
import { resolve } from "node:path";
import jsdom from "jsdom";
const { JSDOM } = jsdom;

export function ogTags(doc) {
  return Object.fromEntries([...doc.querySelectorAll('meta[property^="og:"]')].map((m) => [m.getAttribute("property"), m.getAttribute("content")]));
}

export async function compare(dir) {
  const file = resolve(dir, "index.html");
  const html = readFileSync(file, "utf8");
  const raw = ogTags(new JSDOM(html).window.document);                       // scripts are not run
  const dom = new JSDOM(html, { url: "file://" + file, runScripts: "dangerously", resources: "usable" });
  await new Promise((r) => dom.window.addEventListener("load", r));
  const rendered = ogTags(dom.window.document);
  const missing = Object.keys(rendered).filter((k) => !(k in raw));
  return { raw, rendered, missing };
}

if (import.meta.url === `file://${process.argv[1]}`) {
  const r = await compare(process.argv[2] ?? ".");
  console.log("Raw HTML (what most crawlers read):", Object.keys(r.raw).length ? r.raw : "no og: tags");
  console.log("After JavaScript (what a browser shows):", r.rendered);
  console.log(r.missing.length ? `FAIL: ${r.missing.join(", ")} only exist after JavaScript runs` : "OK: every og: tag is already in the raw HTML");
  process.exitCode = r.missing.length ? 1 : 0;
}

Running it on the page above gives this:

Raw HTML (what most crawlers read): no og: tags
After JavaScript (what a browser shows): {
  'og:title': 'Notes on small sites',
  'og:description': 'Short, tested write-ups.',
  'og:image': 'https://example.github.io/cover.png'
}
FAIL: og:title, og:description, og:image only exist after JavaScript runs

The raw HTML has no og: tags at all. After JavaScript there are three. The script exits with an error code so you can use it as a check before you push. The same comparison is useful for a page built by a framework: if the tags only exist in the second list, you have this problem.

The fix: write the tags into the HTML

The cure is boring and it works. Put the tags in the file. For a static page that means writing them in the head:

<meta property="og:title" content="Notes on small sites">
<meta property="og:description" content="Short, tested write-ups.">
<meta property="og:image" content="https://example.github.io/cover.png">

Run the same script on the fixed page:

Raw HTML (what most crawlers read): {
  'og:title': 'Notes on small sites',
  'og:description': 'Short, tested write-ups.',
  'og:image': 'https://example.github.io/cover.png'
}
After JavaScript (what a browser shows): {
  'og:title': 'Notes on small sites',
  'og:description': 'Short, tested write-ups.',
  'og:image': 'https://example.github.io/cover.png'
}
OK: every og: tag is already in the raw HTML

Now both lists are the same. The browser sees the tags and so does the crawler.

If you have many pages

Writing the tags by hand for ten pages is fine. For fifty it is a chore, and a typo in one of them is easy to miss. There are two common ways out, both of which end with real tags in real HTML.

  • A small build step. A script reads a list of pages and writes each HTML file with its own tags filled in from a template. The output is committed, and GitHub Pages serves the files as they are.
  • A static site generator. Jekyll, which GitHub Pages builds for you, and other generators write tags at build time, so the result is real HTML. If you use a generator, check its output rather than the source, because a theme may set the tags to something you did not expect.

A single-page app on GitHub Pages has the same problem: unless the build pre-renders pages, every route returns the same HTML shell, and every shared link gets the same card.

Tests for the checker

The comparison script has three tests: tags written in the HTML are visible without JavaScript, tags added by a script exist only after it runs, and a tag that a script only overwrites is not reported as missing. They run with node --test:

✔ tags written in the HTML are visible without JavaScript (89.456802ms)
✔ tags added by a script exist only after it runs (19.740153ms)
✔ a tag in the HTML that a script only overwrites is not reported missing (16.760953ms)
ℹ tests 3
ℹ pass 3
ℹ fail 0

The third test came from a mistake of my own. A page can have the tag in HTML and a script that edits its content. In that case the crawler sees the original value, not the edited one. The checker reports that as fine, because the tag exists, but it also keeps both values so you can see the difference.

Check the published page, not only your copy

After you push, wait for GitHub Pages to publish. Then paste the live address into a meta tag checker, which reads the tags in the HTML the server sends. If the tags you expect are not listed, you have the problem described above. For the finished card, an Open Graph checker shows the title, description and picture a chat app will build.

If a chat app still shows an old card, do not change anything. It has a saved copy. Try a different page of the same site, or wait a day.

Summary

  • The inspector shows the page after JavaScript. A crawler usually does not run it.
  • Compare the raw HTML with the rendered page to find tags that only exist after scripts run.
  • Write share tags into the HTML itself, by hand, with a template or with a generator.
  • Check the live page with a tool that reads the server's HTML.

The fix takes minutes. Finding it takes longer when the page works perfectly in your own browser.
